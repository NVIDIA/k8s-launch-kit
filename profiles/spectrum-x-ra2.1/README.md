# Spectrum-X Multi-Rail Profile (RA2.1, Network Operator 26.1)

## Overview

This profile targets **SPC-X RA2.1** on **Network Operator 26.1**. It is the
sibling of the `spectrum-x-ra2.2` profile, which targets **RA2.2** on **26.4+**.
The two profiles are mutually exclusive: pick the right one by passing the
RA version as the value of `--spectrum-x` (e.g. `--spectrum-x RA2.1` selects
this profile).

26.1 does not yet have the consolidated `SpectrumXRailPoolConfig` v1alpha2
CRD, so this profile renders the full chain of SR-IOV operator CRDs:

- `SriovNetworkPoolConfig` (per group, scoped via `nodeSelector`) — DOCA OVS
  hardware-offload config
- `SriovNetworkNodePolicy` (per rail or per rail-plane) — bridges, VFs, eswitch
- `OVSNetwork` (per rail or per rail-plane) — NetworkAttachmentDefinitions
- `CIDRPool` (per rail or per rail-plane) — nv-ipam pod IP allocations
- `SpectrumXRailPoolConfig` v1alpha1 (per rail or per rail-plane) — glue
  resource referencing the SR-IOV node policy and the CIDR pool

`NicFirmwareSource` and `NicFirmwareTemplate` are operator-side concerns and
are not generated by l8k.

## When to use

- Cluster ships ConnectX-8, ConnectX-9, or BlueField-3 SuperNICs
- You're deploying **Network Operator v26.1**. Pass
  `--network-operator-release 26.1` explicitly — under `--spectrum-x RA2.1`
  any other release errors out at the CLI gate.
- You're running **Spectrum-X RA2.1** firmware

If you've selected `--network-operator-release 26.4` or later, use the
`spectrum-x-ra2.2` profile instead — the RA2.1 profile's `maxNetworkOperatorRelease`
gate will reject it.

## Multiplane modes

Same set as the RA2.2 profile: `none`, `swplb`, `hwplb`.

- `swplb` — each rail explodes into per-plane policies, with
  `bridge.groupingPolicy: perPF`. One PF per `SriovNetworkNodePolicy`,
  `metadata.name: rail-{i}-plane-{p}`,
  `resourceName: rail_{i}_plane_{p}`. No `devlinkParams` (each PF runs as
  an independent OVS bridge).
- `hwplb` / `none` — one policy per rail with
  `bridge.groupingPolicy: all`, all of a rail's PF netdevs in `pfNames`,
  and `devlinkParams.params.esw_multiport: "true"` on the PF.

## Generated CRDs

| File                                     | CRD                          | Multiplicity                            |
|------------------------------------------|------------------------------|-----------------------------------------|
| `10-nicclusterpolicy.yaml`               | NicClusterPolicy             | 1 cluster-wide                          |
| `25-nicinterfacenametemplate.yaml`       | NicInterfaceNameTemplate     | 1 per group (or per machine on disagree)|
| `30-nicconfigurationtemplate.yaml`       | NicConfigurationTemplate     | 1 per group                             |
| `40-sriovnetworkpoolconfig.yaml`         | SriovNetworkPoolConfig       | 1 cluster-wide                          |
| `50-sriovnetworknodepolicy.yaml`         | SriovNetworkNodePolicy       | 1 per rail (per rail-plane in swplb)    |
| `55-ovsnetwork.yaml`                     | OVSNetwork                   | matches 50-                             |
| `60-cidrpool.yaml`                       | CIDRPool (nv-ipam)           | matches 50-                             |
| `80-spectrumxrailpoolconfig.yaml`        | SpectrumXRailPoolConfig (v1alpha1) | matches 50-                       |
| `90-example-daemonset.yaml`              | DaemonSet (example workload) | 1 per group                             |

Each `NicConfigurationTemplate` is rendered per source hardware group and
selects both the NIC type and PCI addresses derived from east-west PFs. The
intersection prevents a north-south DPU from receiving Spectrum-X settings
when it reports the same device ID as an east-west SuperNIC.

`60-cidrpool.yaml` derives complete IPv4 or IPv6 CIDRPools from the topology
file. IPv4 uses a `/31` per node with gateway index `0`. IPv6 uses the standard
Spectrum-X `/64` per-node layout with leaf gateway `::2`, gateway index `2`,
and a `/40` pool per rail or rail-plane. IPv6 routes are `/32` for one plane
and `/24` for two or four planes.

## NCP differences vs the RA2.2 profile

26.1's NCP shape is leaner:
- No `nicConfigurationOperator.nicFirmwareStorage` block
- No `spectrumXOperator.xPlane` block

If you maintain a custom NCP and have to bridge between the two releases,
keep these blocks gated on the release line.

## Required helm values for the Network Operator (26.1)

```yaml
sriovNetworkOperator:
  enabled: true

maintenanceOperator:
  enabled: true

sriov-network-operator:
  sriovOperatorConfig:
    configDaemonNodeSelector:
      network.nvidia.com/operator.nic-configuration.wait: "false"
    featureGates:
      manageSoftwareBridges: true
    disablePlugins:
    - mellanox
```

## Generate

```bash
l8k generate \
  --user-config <cluster-config.yaml> \
  --spectrum-x RA2.1 \
  --multiplane-mode hwplb --number-of-planes 2 \
  --topology-scheme 2-tier --ip-version ipv6 \
  --topology-file ./topology.json \
  --network-operator-release 26.1 \
  --save-deployment-files ./deployment
```

## Notes

- **CIDRPool size limits**: each CRD has a 1.5MB etcd object cap. With
  `kubectl apply --server-side` you get ~10,105 nodes per pool; with the
  default client-side `kubectl apply` it drops to ~6,424.
- **RDMA exclusive mode**: not set in this profile. If you need it, add
  `rdmaMode: exclusive` under `SriovNetworkPoolConfig.spec` — note this
  requires a node reboot and cannot coexist with active rdma namespaces.
